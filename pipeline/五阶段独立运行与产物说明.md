# 五个阶段：独立运行与产物说明

> 说明：`run.sh` 一键编排五个阶段，但每一阶段都可独立运行、独立诊断、断点续跑。

---

## 1. 结论

五个阶段都能独立运行，每个阶段有独立脚本、独立输入、独立输出。设计上分成两条互不依赖的分支：

- **角色分支**：①绑骨/蒙皮 → ②清理/语义化，只需要 `character.glb`。
- **动作分支**：③动作提取 → ④动作标准化，只需要 `action.mp4`。
- **⑤重定向/烘焙** 是两条分支的汇合点，同时需要 ② 的 clean GLB 与 ④ 的 NPZ。

正因为「角色外观」「标准骨架+蒙皮」「与外观无关的动作数据(NPZ)」三类资产解耦，
同一角色可换多套动作，同一段动作也能重定向给不同角色。

---

## 2. 各阶段输入/输出总览

| 阶段 | 独立入口脚本 | 输入 | 输出 |
| --- | --- | --- | --- |
| ① 固定骨架/蒙皮 | `create_fixed_smpl22_skeleton.py` + `run_skintokens_offline.py` | `character.glb` | 固定 SMPL-22 输入 GLB + SkinTokens 蒙皮 GLB + 拟合报告 |
| ② 契约验收/语义化 | `prepare_and_test_rig.py`（配 `inspect_rig.py` 验收） | ①的固定骨架和 raw GLB | clean GLB + 压力测试 GLB + 契约诊断 JSON |
| ③ 动作提取 | GVHMR `demo.py`（直接调用） | `action.mp4` | `hmr4d_results.pt` + 可视化 mp4 + 预处理缓存 |
| ④ 动作标准化 | `extract_gvhmr_motion.py` | ③的 `.pt` | SMPL-22 NPZ + manifest JSON |
| ⑤ 重定向/烘焙 | `apply_gvhmr_motion.py` | ②的 clean GLB + ④的 NPZ | 最终动画 GLB + 报告 JSON + QA 渲染图 |

---

## 3. 逐阶段产生的文件

### ① 固定 SMPL-22 / SkinTokens 蒙皮

```
rigging/character_skeleton_input.glb  # 拟合到模型的固定 smpl22-mixamo-v1 + 占位权重
rigging/character_skeleton_fit.json   # 中轴、包围盒、关节坐标和拟合尺度
rigging/character_rigged_raw.glb      # SkinTokens 仅生成蒙皮后的22骨角色
logs/00_fixed_skeleton.log            # 固定骨架拟合日志
logs/01_skintokens.log                # tee 日志
```

SkinTokens 必须使用 `--use-skeleton --use-transfer`。固定骨架是模型输入前缀，SkinTokens
只预测该骨架的蒙皮权重，不再自由生成骨数和父子图。包装器还会在GPU推理前验证输入恰好有
一个名为 `Armature` 的 skin 和22个joint。

### ② 清理/语义化 — `prepare_and_test_rig.py`

> ⚠️ 改名**前**先经过固定契约门禁：以阶段①A的语义骨架为参考，根据父子树和关节位置
> 反推 SkinTokens/glTF 可能重排后的joint名字，再验证22骨完整父子图、左右语义、骨头与
> 权重空间距离、每顶点最多4个权重及权重归一化。不能使用固定 `bone_N` 编号猜语义。

```
rigging/character_rigged_clean.glb    # 语义化骨骼(mixamorig:*)， 语义化、清理后、无动画，用于喂给 ⑤ 重定向
rigging/character_rig_test.glb        # 只用来验证蒙皮权重是否正常（视频里看到角色能正常摆手抬腿），不进入主线
renders/rig_test/*.png                # front/back/left/three_quarter 四视图
logs/02_topology_diagnostic.json      # 拓扑门禁诊断报告
```

> 另外 `inspect_rig.py` 单独运行会产出 `character_rig_summary.json`，用于权重覆盖验收；
> 一键脚本未将其接进主链路。

### ③ 动作提取 — GVHMR `demo.py`

```
motion/gvhmr/<video_stem>/hmr4d_results.pt   # 核心：SMPL-X 参数
motion/gvhmr/<video_stem>/0_input_video.mp4  # 标准化后的输入
motion/gvhmr/<video_stem>/1_incam.mp4        # 机内重建可视化
motion/gvhmr/<video_stem>/2_global.mp4       # 世界坐标重建可视化
motion/gvhmr/<video_stem>/preprocess/*.pt    # bbx/vitpose/vit_features 缓存
logs/03_gvhmr.log
```

> 远程无 ffmpeg，`1_incam.mp4` / `2_global.mp4` 的横向拼接可能失败，
> 但**不影响** `hmr4d_results.pt`；脚本以 `hmr4d_results.pt` 是否存在判定核心动作成功。

### ④ 动作标准化 — `extract_gvhmr_motion.py`

```
motion/<video_stem>_smpl22.npz            # 可移植动作：rotations[T,22,3,3] + translations + source_height + fps
motion/<video_stem>_motion_manifest.json  # shape/帧数/身高/位移范围报告
logs/04_extract_motion.log
```

### ⑤ 重定向/烘焙 — `apply_gvhmr_motion.py`

```
motion/character_<video_stem>_animated.glb   # ★最终产物：22 骨 + GVHMR_Action 动画 + PBR
motion/<video_stem>_retarget_report.json     # 缩放比例/帧数/FPS/映射数量报告
renders/retarget/gvhmr_frame_*.png           # 关键帧 QA（1、F/3、2F/3 帧）
logs/05_retarget.log
```

---

## 4. 独立性判断

- **①② 走「角色分支」**：只需要 `character.glb`，不依赖视频，可单独跑完得到 `character_rigged_clean.glb`。
- **③④ 走「动作分支」**：只需要 `action.mp4`，不依赖角色，可单独跑完得到 `<video_stem>_smpl22.npz`。
- **⑤ 是汇合点**：同时需要 ② 的 clean GLB + ④ 的 NPZ，产出最终动画 GLB。
- 两个分支互不依赖、可并行；这也是「断点续跑、同一动作复用给不同角色」的设计基础。

## 5. 完整 run 目录结构

一键脚本为每个 run 建立如下目录：

```
<output_dir>/
├── rigging/
│   ├── character_rigged_raw.glb
│   ├── character_skeleton_input.glb
│   ├── character_skeleton_fit.json
│   ├── character_rigged_clean.glb
│   └── character_rig_test.glb
├── motion/
│   ├── gvhmr/<video_stem>/
│   │   ├── 0_input_video.mp4
│   │   ├── 1_incam.mp4
│   │   ├── 2_global.mp4
│   │   ├── hmr4d_results.pt
│   │   └── preprocess/*.pt
│   ├── <video_stem>_smpl22.npz
│   ├── <video_stem>_motion_manifest.json
│   ├── <video_stem>_retarget_report.json
│   └── character_<video_stem>_animated.glb
├── renders/
│   ├── rig_test/*.png
│   └── retarget/*.png
└── logs/
    ├── 00_fixed_skeleton.log
    ├── 01_skintokens.log
    ├── 02_prepare_rig.log
    ├── 02_topology_diagnostic.json
    ├── 03_gvhmr.log
    ├── 04_extract_motion.log
    └── 05_retarget.log
```

## 6. 分阶段手动执行

任一阶段失败时，可按手册第 14 节「分阶段手动执行清单」单独重跑定位。
以远程机器为例，先设置变量：

```bash
WORK=/home/naqi/hackday-character-pipeline
RUN=$WORK/runs/manual_test
VIDEO=$WORK/inputs/action.mp4
CHARACTER=$WORK/inputs/character.glb

mkdir -p "$RUN"/{rigging,motion,renders,logs}
```

### 阶段 ①A 拟合固定 SMPL-22 骨架

```bash
/usr/local/bin/blender --background --python-exit-code 1 \
  --python "$WORK/pipeline/scripts/create_fixed_smpl22_skeleton.py" -- \
  --input "$CHARACTER" \
  --template "$WORK/pipeline/config/smpl22_skeleton.json" \
  --output "$RUN/rigging/character_skeleton_input.glb" \
  --report "$RUN/rigging/character_skeleton_fit.json" \
  2>&1 | tee "$RUN/logs/00_fixed_skeleton.log"
```

默认人体中轴从上半身中央截面估计，避免披风、长发、武器和背包把骨架拖到包围盒后方。
四肢不再只按整体包围盒比例缩放：上臂、肘、腕使用窄 X 截面的稳健体积中心，双脚使用最低轮廓切片的左右中心，膝盖在髋部与脚中心间插值。极端资产可通过 `--body-center-y` 手工覆盖；所有自动地标及回退原因都会写入 `character_skeleton_fit.json`。

> Blender 中手、头、脚末端的 leaf bone tail 只负责可视化，不是第 23 个关节，也不参与蒙皮。glTF 不保存 leaf tail，重新导入时 Blender 可能再次按父骨长度显示；主管线内部会将其修成短的语义方向线。

### 阶段 ①B SkinTokens 固定骨架蒙皮

```bash
cd /home/naqi/SkinTokens

.venv/bin/python -u "$WORK/pipeline/scripts/run_skintokens_offline.py" \
  --skintokens-home /home/naqi/SkinTokens \
  --input "$RUN/rigging/character_skeleton_input.glb" \
  --output "$RUN/rigging/character_rigged_raw.glb" \
  --seed 0 \
  --use-skeleton \
  --use-transfer \
  2>&1 | tee "$RUN/logs/01_skintokens.log"
```

### 阶段 ② 清理/语义化（含压力测试）

```bash
/usr/local/bin/blender --background --python-exit-code 1 \
  --python "$WORK/pipeline/scripts/prepare_and_test_rig.py" -- \
  --input "$RUN/rigging/character_rigged_raw.glb" \
  --reference-skeleton "$RUN/rigging/character_skeleton_input.glb" \
  --clean-output "$RUN/rigging/character_rigged_clean.glb" \
  --animated-output "$RUN/rigging/character_rig_test.glb" \
  --render-dir "$RUN/renders/rig_test" \
  --diagnostic "$RUN/logs/02_topology_diagnostic.json" \
  2>&1 | tee "$RUN/logs/02_prepare_rig.log"
```

> 此脚本会证明 SkinTokens 保留了固定 SMPL-22 契约，并检查权重覆盖、归一化、左右侧和
> 骨头到加权顶点中心的距离。四肢使用 0.35 身高的硬阈值；躯干/头部可能驱动披风、长裙、
> 长发和背包，0.30 后记录 warning、0.50 后才硬失败。失败时完整权重报告也会先写入诊断 JSON。
> 应检查固定骨架拟合和 `use_skeleton` 日志，不能随机重采样绕过。

inspect_rig.py 单独运行会产出 character_rig_summary.json，用于权重覆盖验收，命令如下：
```bash
/usr/local/bin/blender --background --python-exit-code 1 \
  --python "$WORK/pipeline/scripts/inspect_rig.py" -- \
  --input "$RUN/rigging/character_rigged_raw.glb" \
  --output "$RUN/rigging/character_rig_summary.json"
```

### 阶段 ③ GVHMR 动作提取

```bash
cd /home/naqi/GVHMR

env PYTHONPATH=/home/naqi/GVHMR \
  TORCH_FORCE_NO_WEIGHTS_ONLY_LOAD=1 \
  .venv310/bin/python tools/demo/demo.py \
    --video "$VIDEO" \
    --output_root "$RUN/motion/gvhmr" \
    --static_cam \
    2>&1 | tee "$RUN/logs/03_gvhmr.log"
```

移动机位去掉 `--static_cam`。若最后只因 ffmpeg 失败，确认核心文件存在即可：

```bash
VIDEO_BASE=$(basename "$VIDEO")
VIDEO_STEM=${VIDEO_BASE%.*}
GVHMR_RESULT="$RUN/motion/gvhmr/$VIDEO_STEM/hmr4d_results.pt"
ls -lh "$GVHMR_RESULT"
```

### 阶段 ④ 动作标准化

```bash
cd /home/naqi/GVHMR

env PYTHONPATH=/home/naqi/GVHMR \
  TORCH_FORCE_NO_WEIGHTS_ONLY_LOAD=1 \
  .venv310/bin/python "$WORK/pipeline/scripts/extract_gvhmr_motion.py" \
    --input "$GVHMR_RESULT" \
    --output "$RUN/motion/${VIDEO_STEM}_smpl22.npz" \
    --manifest "$RUN/motion/${VIDEO_STEM}_motion_manifest.json" \
    2>&1 | tee "$RUN/logs/04_extract_motion.log"
```

### 阶段 ⑤ 重定向/烘焙

```bash
/usr/local/bin/blender --background --python-exit-code 1 \
  --python "$WORK/pipeline/scripts/apply_gvhmr_motion.py" -- \
  --character "$RUN/rigging/character_rigged_clean.glb" \
  --motion "$RUN/motion/${VIDEO_STEM}_smpl22.npz" \
  --output "$RUN/motion/character_${VIDEO_STEM}_animated.glb" \
  --report "$RUN/motion/${VIDEO_STEM}_retarget_report.json" \
  --preview-dir "$RUN/renders/retarget" \
  2>&1 | tee "$RUN/logs/05_retarget.log"
```
